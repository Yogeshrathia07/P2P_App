# P2P Doubt Board

## 1. Project Overview

P2P Doubt Board is a decentralised web application that allows students to share doubts and answers directly with each other. It uses WebRTC technology to establish a peer-to-peer connection between two devices.

Messages are exchanged directly between connected browsers instead of passing through a central application server.

## 2. Objectives

- To create a platform for students to share doubts and answers.
- To establish direct communication between two devices.
- To understand the working of WebRTC.
- To implement frontend development concepts using HTML, CSS and JavaScript.
- To store messages locally on the user's device.

## 3. Technologies Used

| Technology | Purpose |
|---|---|
| HTML5 | Creates the webpage structure |
| CSS3 | Styling and responsive design |
| JavaScript | Application logic and user interaction |
| WebRTC | Peer-to-peer communication |
| RTCDataChannel | Transfers messages between devices |
| localStorage | Stores messages locally |
| STUN Server | Helps discover possible direct network routes |
| GitHub Pages | Website hosting |

## 4. Project Features

- Create a peer-to-peer connection.
- Exchange connection codes manually.
- Send doubts and answers between two connected devices.
- Display messages on the discussion board.
- Save messages in browser localStorage.
- Synchronise available message history between connected peers.
- Prevent duplicate messages using unique message IDs.
- Responsive user interface.

## 5. How to Run the Project

1. Download or clone the project repository.
2. Open the project folder in Visual Studio Code.
3. Open `index.html` using Live Server.
4. Open the application on two devices or browsers.
5. Enter your name and create a connection on Device A.
6. Copy the generated offer code and send it to Device B.
7. Paste the offer code on Device B and accept the connection.
8. Copy the answer code generated by Device B.
9. Send the answer code back to Device A.
10. Paste the answer code on Device A and accept the connection.
11. After connection, both students can exchange doubts and answers.

## 6. Decentralised System Problems Addressed

1. **Central server dependency:** Messages are exchanged directly between connected browsers using WebRTC instead of a central messaging server.

2. **Data storage dependency:** Each device maintains its own message history using localStorage.

3. **Late joining participants:** A newly connected peer can request and receive the available message history from the other peer.

4. **Duplicate messages:** Unique message IDs prevent the same message from being added multiple times.

## 7. Development Challenges and Solutions

1. **Establishing a peer-to-peer connection:** Initially, connecting two browsers directly was challenging. WebRTC offer and answer exchange was implemented to establish the connection.

2. **Exchanging connection details:** Both devices needed connection information before communication could begin. A manual copy-and-paste method was implemented for exchanging offer and answer codes.

3. **Handling messages between devices:** Sending and receiving messages required a communication channel. RTCDataChannel was used to transfer messages directly.

4. **Saving messages after refreshing:** Messages could disappear when the webpage was refreshed. localStorage was implemented to preserve message history on each device.

5. **Avoiding duplicate messages:** Synchronising message history could cause repeated entries. Unique message IDs were used to identify and prevent duplicate messages.

## 8. Limitations

- The application currently supports one-to-one peer connections.
- Connection details must be exchanged manually.
- Direct connections may fail on restricted networks because only a STUN server is configured.
- Messages are stored locally and may be lost if browser storage is cleared.
- There is no central database for permanent message storage.

## 9. Security and Privacy

- Messages are transferred through a WebRTC data channel.
- User names are not verified.
- Connection codes should only be shared with trusted participants.
- The application does not use a central database to store messages.
